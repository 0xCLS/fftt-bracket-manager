### A. Record Result X
- `openDialog(build, {label, closeButton})` adds an accessible `×` button (`aria-label="Close"`, 44×44 px, sticky top-right so it stays reachable in the scrolling mobile sheet). It is attached to the dialog itself, **outside** the re-rendered body, so it remains available while saving, in error states, and during **result review**.
- It calls the **same `close()`** as the retained bottom **Close** button. `close()` is `dlg.close()`; the existing `close` listener restores focus to the opener, and the existing prepared-score cancel runs. Nothing is sent by closing; saved games and the unfinished match are server-side and untouched. Escape (native `cancel`) is unchanged.
- Initial keyboard focus stays on the first working control, not the X.
- Applied to the singles Record Result dialog and the Mixed-Skill Doubles scoring dialog. The scoring form itself is not redesigned. Confirm dialogs, walkover, correction and withdrawal dialogs are unchanged (they already have Cancel).

### B. Stray `null`
**Root cause:** `clear(body).append(…, count > 0 ? h('p', …) : null, …)` in the singles dialog. `Element.append(null)` coerces `null` to the **text "null"**, whereas the project's `h()` helper skips null children. With no saved game (`count === 0`) the literal word appeared above the Close / Review buttons. The same unsafe `clear(body).append(…)` pattern existed in the singles review, the doubles form and the doubles review.
**Fix:** those four renders now use the existing null-safe `fill(body, …)` helper (`dom.mjs`). No scoring logic changed. **Regression test:** `tests/e2e/staff_dialog_x_null_rename_browser.test.mjs` fails on the old code with *"dialog text must not contain a literal "null""* and passes on the fix (verified both ways).

### C. Completed-event rename
- **Server (`fftt_private.rename_completed_event_v1` + `public.fftt_rename_completed_event_v1(p_event_id, p_expected_name, p_name)`):** `v3_begin` row-locks the event (`FOR UPDATE`), requires role `organizer` for **that event** and lifecycle exactly `complete`. Name is trimmed, 1–120 characters, no control characters. **Optimistic concurrency:** the caller sends the name it saw; a different current name raises `conflict/name-changed` and nothing is overwritten. An unchanged name is a no-op (no revision bump, no audit). The function updates **only** `events.event_name`; lifecycle, date, tables, visibility, players, brackets, matches, scores, standings and results are never touched. The revision advances once.
- **Audit:** one `event_updated` row (existing operation — `audit_events_operation_check` is deliberately **not** altered) with `before_state {name,date,tables}`, `after_state {name,date,tables,completed_rename:true}`, `actor_id = auth.uid()`, `created_at`, and the new `event_revision`.
- **Authorization:** `anon` has no execute right; `authenticated` does, but the role/lifecycle check inside is the authority. Scorer, Bracket Manager, outsider and an organizer of a *different* event are refused (`42501`). Draft, active and archived events are refused (`conflict/lifecycle`); an archived event must be restored first. The ordinary `fftt_update_event_v3` still refuses completed events, so **date, table count, scoring and lifecycle editing are not broadened**.
- **UI:** only inside **Overview › Set up your tournament**. For an Organizer on a Completed event the date and tables fields are disabled, an explanatory note is shown and the button reads **Rename completed event**. No title pencil and no separate Edit Event popup. Public/Spectator surfaces read the same `event_name`, so a published completed event would show its new name.

### D. Withdraw-before-play visibility (server-confirmed, fail closed)
**Problem found in the live walkthrough:** the control was shown whenever no match was *complete* (`played === 0`), so it was still offered after a game was saved. The server refused it correctly, but the control should not have been offered.

**Change.** A new **read-only** server function `fftt_preplay_withdrawal_eligibility_v1(p_event_id)` (private `SECURITY DEFINER` function + `SECURITY INVOKER` public wrapper; `anon` has no execute) returns `{event_id, eligible, reason, generation, revision}` using **exactly the event-wide conditions of `withdraw_preplay_v7`**: lifecycle `active`; an active Championship in the current generation; **any** completed match, accepted result submission or score decision; **any** saved game or game-progress decision (event-wide, so **superseded bracket generations count**); a Consolation bracket; a Doubles finale; and at least three checked-in players so two can remain. Only the Organizer or Bracket Manager **of that event** may ask (Scorer, outsider, anonymous and another event's organizer get `42501`). It writes nothing (no audit row, no revision bump). `reason` is a stable code (`lifecycle`, `no-active-championship`, `results-exist`, `saved-games-exist`, `consolation-exists`, `doubles-exists`, `not-enough-players`). **`withdraw_preplay_v7` itself and every server safeguard are unchanged.**

**Client rule (`core.preplayWithdrawal()`).** The control is actionable only when **all** hold: Organizer or Bracket Manager; signed in with a loaded snapshot; an active Championship in view; a server verdict exists, is for **this event**, for **this bracket generation and revision** (the same ones the page is showing), and says `eligible`. Otherwise it is **not rendered**: loading, no verdict, failed or malformed read, the function not installed, a verdict for another event/generation/revision, a Scorer, no bracket. The verdict is refreshed with every full refresh (any revision change), is dropped as soon as this device starts saving a game, and is **re-checked with the server at click time**: the dialog opens only on a fresh eligible answer, otherwise a plain-language message explains why and the offer is withdrawn. The existing server refusal remains the final authority even if the UI is bypassed.

**Deployment consequence:** a Staff build deployed **before** the eligibility SQL cannot read the verdict and will hide the control entirely (safe, but a visible regression of the deployed feature). Hence SQL first.

### E. Result-review wording
The singles review said "The completed games are already saved" even when scores had only been typed on the form. It now distinguishes the two cases: **games saved one by one and confirmed by the server** ("These games were already saved one by one…") versus **scores typed on this form** ("…have not been saved as individual games. Nothing is recorded until you confirm…"). The Mixed-Skill Doubles review is always built from server-confirmed games and now says so. Scoring behavior is unchanged.

### F. Scoring dialogs could stall while a background poll ran (found by CI, fixed here)
**Symptom.** GitHub fast-check run 42763342815 failed two of this PR's own browser tests (142/144): the Record Result dialog never reached "Game 2 · 11–5 · Saved" after reopening, and a second match never showed "Game 1 · Unconfirmed". The dialog stayed on "Loading verified game scores…" with the message "Completed-game records are unavailable. Nothing was changed; check the connection and migration." This is the same message seen **once on the live system** during the 2026-11-10 walkthrough (observation 4.3-c), which was therefore a real, not a test, effect.

**Root cause (a genuine application defect, pre-existing; this PR's earlier change made it more likely).** The Staff session allows one privileged operation at a time. Background polling passes `wait: false` and is *skipped* when the session is busy, which is correct for a poll. But three **person-initiated** calls also passed `wait: false`: reading a match's saved games when its scoring dialog opens (`readGameProgress`), reading the doubles dialog's games (`readDoublesProgress`) and the receipt check after saving a game (`checkPendingGame`). If a poll refresh was in flight at that moment, the person's read was dropped as "busy" and reported as "unavailable"; the dialog had no retry and stayed stuck. The slower the connection or runner, the longer a refresh holds the lock, so the race is far likelier on CI and on weak venue Wi-Fi. This PR's change D added one more request (the withdrawal verdict) to every full refresh, lengthening that window, which is why it first surfaced here.

**Fix.** Those three calls no longer pass `wait: false`, so a person's action **queues** behind the poll (a poll never queues behind a person). Only the polling `refresh` may still be skipped. No scoring rule, receipt logic or write path changed; a skipped receipt check could previously also leave a saved game needlessly "unconfirmed".

**Reproduction and proof (not a timeout change, no assertion was weakened).**
- Core level, deterministic: hold the lock with a slow refresh, then open a match. Before the fix: `Completed-game records are unavailable…`; after: loads. `tests/e2e/interactive_reads_not_skipped_core.test.mjs` also records how every session call schedules itself and asserts that only `refresh` may opt out of queueing (it failed on the old code for exactly `readGameProgress`, `readDoublesProgress` and `checkPendingGame`).
- Browser level: with 250 ms added to every request, the unfixed code fails the scoring-dialog flow **3/3**; with the fix it passes **3/3** (`tests/e2e/staff_dialog_slow_network_browser.test.mjs`, now permanent).
- The two CI-failing tests did not fail on the faster development machine even at CI's `--test-concurrency=2` (it needs a slow lock holder), which is why they were missed locally.
